# 🗄️ Database Migrations

## 1. نظرة عامة

الـ Migrations هي ملفات SQL تُستخدم لتعديل بنية قاعدة البيانات وإضافة الجداول والأعمدة والقيود والفهارس، أو تحديث البنية الحالية دون الحاجة إلى إعادة إنشاء قاعدة البيانات بالكامل.

تنقسم تحديثات قاعدة البيانات في مشروع **OnixEdres** إلى:

1. **Schema الأساسي:** ملف `databaseOnixEdresSchema_2026_11_09.sql`.
2. **Migrations الإضافية:** ملفات SQL الموجودة داخل مجلد `migrations/`.
3. **Migrations البيانات والإعدادات:** سكربتات موجودة داخل مجلد `scripts/`.

> **مهم:** لا تقم بإعادة إنشاء قاعدة البيانات أو حذف بيانات الشركات الحالية عند تطبيق التحديثات. استخدم ملفات Migration المخصصة للتغيير المطلوب.

# 3. متطلبات ما قبل التنفيذ

قبل تشغيل أي Migration يجب التأكد من الآتي:

- الاتصال بقاعدة البيانات الصحيحة.
- توفر نسخة احتياطية حديثة.
- مراجعة ملف SQL قبل تنفيذه.
- التأكد من عدم وجود Migration سابقة غير مكتملة.
- التأكد من أن التغيير متوافق مع إصدار التطبيق الحالي.
- عدم تشغيل ملفات غير معروفة أو غير مراجعة على قاعدة الإنتاج.

## 3.1 النسخ الاحتياطي

يجب أخذ نسخة احتياطية قبل إجراء أي تعديل على قاعدة البيانات.

### باستخدام pg_dump

    pg_dump -U postgres -d your_db -F c -f backup_before_migration.dump

استبدل `your_db` باسم قاعدة البيانات الفعلية.

### استعادة النسخة الاحتياطية

    pg_restore -U postgres -d your_db --clean --if-exists backup_before_migration.dump

**تحذير:** أمر الاستعادة أعلاه قد يحذف أو يستبدل كائنات موجودة في قاعدة البيانات المستهدفة. لا تستخدمه على قاعدة الإنتاج إلا بعد التأكد من قاعدة الاستعادة والنتائج المتوقعة.

# 4. تشغيل Migrations

## 4.1 تشغيل الملفات على Windows PowerShell

من مجلد المشروع الرئيسي:

    Get-ChildItem .\migrations\2026_11_*.sql |
        Sort-Object Name |
        ForEach-Object {
            Write-Host "Applying $($_.Name)..." -ForegroundColor Cyan

            psql -U postgres -d your_db -v ON_ERROR_STOP=1 -f $_.FullName

            if ($LASTEXITCODE -ne 0) {
                throw "Migration failed: $($_.Name)"
            }

            Write-Host "Completed: $($_.Name)" -ForegroundColor Green
        }

يؤدي استخدام `ON_ERROR_STOP=1` إلى إيقاف تنفيذ ملف SQL عند حدوث خطأ، ويمنع استمرار الحلقة إلى الملف التالي عند فشل التنفيذ.

> **تنبيه:** الترتيب الأبجدي مناسب للقائمة الموثقة أعلاه بسبب تسمية الملفات بالتاريخ، لكن يجب التأكد من اعتماد ترتيب التنفيذ الصحيح ومراجعة الاعتماديات بين الملفات قبل تشغيل المجموعة كاملة.

## 4.2 تشغيل الملفات على Linux / macOS

    for f in migrations/2026_11_*.sql; do
        echo "Applying $f..."

        psql -U postgres -d your_db \
            -v ON_ERROR_STOP=1 \
            -f "$f" || exit 1

        echo "Completed: $f"
    done

بعض التحديثات لا تتعلق ببنية الجداول فقط، بل تضيف بيانات مرجعية أو إعدادات أو صلاحيات.

السكربتات الموثقة:

## 5.1 تحديث الصلاحيات

    node src/scripts/seed-permissions.js

الغرض:

- إضافة الصلاحيات الجديدة.
- تحديث بيانات الصلاحيات حسب منطق السكربت.
- الحفاظ على الصلاحيات الموجودة وفق آلية التنفيذ.

## 5.2 تحديث الإعدادات

    node src/scripts/migrate-settings.js

الغرض:

- إضافة الإعدادات الجديدة.
- تطبيق التحديثات على الشركات الموجودة.

الهدف هو تمييز القيود الناتجة عن أذون الاستلام عن القيود الناتجة عن أنواع المستندات الأخرى.

## 6.8 `2026_11_12_consolidate_journal_source_types.sql`

**الغرض:** توحيد قيود أنواع مصادر القيود المحاسبية.

التغييرات والاختبارات الموثقة:

1. مراجعة قيود CHECK المرتبطة بـ `source_type`.
2. حذف قيد enum المحدد، وليس حذف جميع القيود الأخرى.
3. إضافة قيد CHECK جديد يتضمن 16 نوعاً.
4. اختبار إدراج ثلاثة أنواع جديدة.
5. اختبار رفض نوع غير صالح.

> يجب مراجعة ملف SQL الفعلي للتأكد من طريقة اكتشاف القيود وحذفها، والتأكد من أن الحذف يستهدف القيد المقصود فقط.

## 6.9 `2026_11_12_fix_product_batches_unique.sql`

**الغرض:** معالجة القيد الفريد لدفعات المنتجات.

التغييرات الموثقة:

- التحقق من التكرارات الموجودة.
- إضافة Partial Unique Index.
- معالجة حالات `NULL` و`''` في رقم الدفعة وفق شروط الفهرس.

يجب فحص البيانات الموجودة قبل إضافة الفهرس؛ لأن وجود سجلات متكررة مطابقة لشروطه قد يمنع إنشاءه.

# 7. Idempotency — أمان إعادة التشغيل

يقصد بـ Idempotency أن يؤدي تشغيل Migration أكثر من مرة إلى عدم تكرار التغييرات أو إفساد البيانات.

تتضمن الأساليب المستخدمة في ملفات الترحيل الموثقة:

- `CREATE TABLE IF NOT EXISTS`
- `DO $$ ... $$` مع فحوصات مسبقة.
- `ON CONFLICT DO NOTHING`
- `ALTER TABLE ... DROP CONSTRAINT IF EXISTS`

**تنبيه مهم:** لا يعني وجود هذه الأساليب أن جميع ملفات Migration آمنة تلقائياً لإعادة التشغيل. يجب مراجعة كل ملف SQL واختبار تشغيله مرة ثانية على نسخة تجريبية من قاعدة البيانات.

# 8. Rollback — التراجع عن Migration

Rollback هو إجراء يعيد بعض التغييرات التي أجرتها Migration سابقة.

قد يشمل:

- حذف جدول تمت إضافته.
- حذف عمود تمت إضافته.
- حذف فهرس أو قيد.
- إعادة قيد سابق.
- التراجع عن تغييرات محددة في البيانات.

## 8.1 مثال: التراجع عن أذون التحويل

    BEGIN;

    DROP TABLE IF EXISTS stock_transfer_items CASCADE;
    DROP TABLE IF EXISTS stock_transfers CASCADE;

    COMMIT;

**تحذير:** هذا المثال يحذف الجداول وبياناتها، وقد يؤدي استخدام `CASCADE` إلى حذف كائنات تعتمد عليها.

لا تستخدم هذا المثال على الإنتاج دون مراجعة الاعتماديات والنسخة الاحتياطية.

## 8.2 قواعد Rollback

1. يجب أن يكون لكل Migration إجراء تراجع موثق أو خطة استعادة واضحة.
2. يجب معرفة تأثير التراجع على البيانات الموجودة.
3. لا تستخدم `CASCADE` دون مراجعة العلاقات التابعة.
4. لا تحذف سجلات مالية أو مخزنية تاريخية لمجرد التراجع عن تغيير برمجي.
5. يفضل اختبار Rollback على نسخة من قاعدة البيانات قبل الإنتاج.
6. عند وجود تغييرات بيانات لا يمكن عكسها بأمان، قد تكون Migration تصحيحية جديدة أكثر ملاءمة من التراجع المباشر.

# 9. التحقق بعد التنفيذ

بعد تشغيل Migrations يجب التأكد من وجود الجداول الجديدة.

## 9.1 التحقق من الجداول العشرة الجديدة

    SELECT COUNT(*)
    FROM information_schema.tables
    WHERE table_schema = 'public'
      AND table_type = 'BASE TABLE'
      AND table_name IN (
          'notes',
          'note_items',
          'delivery_notes',
          'delivery_note_items',
          'stock_transfers',
          'stock_transfer_items',
          'stock_adjustments',
          'stock_adjustment_items',
          'goods_receipts',
          'goods_receipt_items'
      );

العدد المتوقع وفق القائمة الموثقة:

    10

## 9.2 عرض الجداول الجديدة

    SELECT table_name
    FROM information_schema.tables
    WHERE table_schema = 'public'
      AND table_type = 'BASE TABLE'
      AND table_name IN (
          'notes',
          'note_items',
          'delivery_notes',
          'delivery_note_items',
          'stock_transfers',
          'stock_transfer_items',
          'stock_adjustments',
          'stock_adjustment_items',
          'goods_receipts',
          'goods_receipt_items'
      )
    ORDER BY table_name;

## 9.3 التحقق من عدد الصلاحيات

    SELECT COUNT(*)
    FROM permissions;

العدد المرجعي المذكور في التوثيق:

    حوالي 132 صلاحية

> العدد تقريبي وليس شرطاً ثابتاً؛ فقد يتغير مع إضافة صلاحيات جديدة أو تعديل النظام.

## 9.4 التحقق من قيود CHECK الخاصة بمصادر القيود

    SELECT
        conname,
        pg_get_constraintdef(oid) AS definition
    FROM pg_constraint
    WHERE conrelid = 'journal_entries'::regclass
      AND contype = 'c'
    ORDER BY conname;

## 9.5 التحقق من فهرس دفعات المنتجات

    SELECT
        indexname,
        indexdef
    FROM pg_indexes
    WHERE schemaname = 'public'
      AND tablename = 'product_batches'
    ORDER BY indexname;

# 11. ملاحظات مهمة

1. النسخ الاحتياطي إلزامي قبل أي Migration على قاعدة الإنتاج.
2. ترتيب التنفيذ مهم، خصوصاً عندما تعتمد Migration على جداول أو قيود سابقة.
3. لا تفترض أن كل Migration آمنة للتشغيل المتكرر دون مراجعة محتواها.
4. يجب توثيق طريقة Rollback لكل Migration.
5. تحديثات الإعدادات والصلاحيات منفصلة عن تحديثات بنية قاعدة البيانات.
6. `migrate-settings.js` يستخدم لتطبيق تحديثات الإعدادات على الشركات الموجودة وفق منطق السكربت.
7. `seed-permissions.js` يستخدم لإضافة أو تحديث الصلاحيات وفق منطق السكربت.
8. `seed.js` مخصص للبيانات التجريبية، ولا ينبغي تشغيله تلقائياً في الإنتاج.
9. يجب اختبار التحديثات على بيئة تطوير أو نسخة احتياطية قبل الإنتاج.
10. يجب إجراء تحقق نهائي من الجداول والقيود والفهارس والصلاحيات بعد التنفيذ.

# 13. تحديث التوثيق

عند إضافة Migration جديدة إلى المشروع يجب:

1. إنشاء ملف باسم واضح يبدأ بالتاريخ.
2. وصف سبب التغيير.
3. توثيق الجداول والأعمدة والقيود والفهارس المضافة أو المعدلة.
4. توضيح أثر التغيير على البيانات الحالية.
5. توثيق متطلبات التنفيذ والاعتماديات.
6. توثيق خطة Rollback أو الاستعادة.
7. إضافة الملف إلى قائمة Migrations في هذا المستند.
8. تحديث `docs/database/schema.md` إذا تغير المخطط.
9. اختبار التغيير على قاعدة بيانات تجريبية.
10. عدم اعتبار Migration مكتملة قبل التحقق من نجاح تنفيذها.

**الهدف:** الحفاظ على قاعدة بيانات مستقرة وقابلة للتطوير، مع حماية بيانات الشركات والمعلومات المالية والمخزنية أثناء التحديثات.
